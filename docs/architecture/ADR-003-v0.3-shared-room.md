# ADR-003 — v0.3 Real Shared Room

- **Status:** accepted
- **Date:** 2026-09-04
- **Branch:** `feature/real-shared-room-v0.3`
- **Supersedes:** the v0.2 prototype server (`server/{domain,store,service,curator,mcp,http,seed}.ts`)
- **Inputs:** [V0_3_RESEARCH.md](./V0_3_RESEARCH.md), [REFERENCE_IMPLEMENTATIONS.md](./REFERENCE_IMPLEMENTATIONS.md)

## Context

v0.2 proved the *idea* of attributed shared memory with proposal-only AI. It did
not prove it end-to-end: React still mutated its own local state, identity was a
self-declared header or a module-scope environment variable, and records and
events were stored as two parallel truths that could drift.

v0.3 makes **one existing problem work end-to-end through the real backend**,
with two humans on two transports, and adds no new conceptual layers.

Research changed one thing about the plan: the MCP layer is written in the v1
idiom against a v2 SDK whose own shape (`McpServerFactory` consumed by both
`serveStdio` and `createMcpHandler`) is the transport-independence this
milestone wanted. So the MCP refactor happens **first**, as a precondition, not
as a cleanup afterwards.

## Decisions

### 1. Transport-independent application/domain service

The domain and application layers take plain values and return plain values.
They import nothing from `node:http`, from the MCP SDK, or from `process.env`.

```
server/
  domain/        types · events · conflicts · projections · policies
  application/   problem-service · contribution-service · curation-service
  persistence/   repository (port) · json-repository (adapter) · seed
  curation/      deterministic · ai-curator
  auth/          actor-context (port) · prototype-auth (adapter)
  mcp/           create-server · register-tools · stdio · http
  http/          api · server
  container.ts   composition root
```

Services are constructed by `createServices(deps)` where `deps` is
`{ repository, clock, ids, curator }`. Every mutating call takes an
`ActorContext` as its first argument. There is no ambient identity, no global
singleton, and no `process.env` read below the entrypoints — which is what makes
one in-process service instance serveable to React, HTTP, MCP and tests
simultaneously.

**Consequence:** the decisive integration test can construct services once and
drive them through both an HTTP adapter and an MCP client. If any layer knew its
transport, that test could not exist.

### 2. HTTP adapter

Plain `node:http` (no framework). It: parses the request, extracts
`Authorization: Bearer`, resolves an `ActorContext`, calls one application
method, maps domain errors to status codes, serialises JSON.

```
GET  /api/problems
GET  /api/problems/:id
GET  /api/problems/:id/updates?since=
GET  /api/problems/:id/conflicts
GET  /api/problems/:id/curation
GET  /api/problems/:id/events
POST /api/problems/:id/contributions
POST /api/curation/:id/accept
POST /api/curation/:id/reject
POST /api/auth/session          # dev-only issuer, see §9
GET  /api/participants          # dev-only roster
GET  /health
```

`x-brainstorm-actor` is **removed**, not deprecated. Leaving it would leave a
path where the caller asserts identity.

### 3. MCP adapter

`createBrainstormServer(services, actor)` returns a configured `McpServer` and
binds no transport. `registerTools(server, services, actor)` is the single
registration site. Two entrypoints consume the same factory:

- `server/mcp/stdio.ts` → `serveStdio(factory)`
- `server/mcp/http.ts` → `createMcpHandler(factory)` mounted via `toNodeHandler`

Every tool declares `inputSchema` **and** `outputSchema` as Zod objects, returns
`content` + `structuredContent`, and reports operation failures as
`{ isError: true }` results rather than thrown exceptions.

Tools: `list_problems`, `get_problem_state`, `get_problem_updates`,
`get_my_contributions`, `get_conflicts`, `propose_contribution`,
`review_curation_proposal`.

**No MCP tool handler touches the repository.** Handlers call application
services only — the same objects the HTTP adapter calls.

### 4. Persistence adapter

**JSON for v0.3** (Option A), behind `EventRepository`:

```ts
interface EventRepository {
  append(events: MemoryEvent[]): Promise<void>
  read(problemId?: string): Promise<MemoryEvent[]>
}
```

Two methods, because that is all an append-only log needs. The store never sees
a contribution, a relation or a conflict — only events — so **storage technology
cannot define the ontology**.

Writes are serialised through an in-process mutex, fixing v0.2's lost-update
bug: two concurrent contributions previously raced on read-modify-write of the
whole file, and one would vanish. That was the only multi-user gap JSON actually
created.

Postgres is deferred with a recorded trigger (V0_3_RESEARCH.md, *Persistence*):
multi-process serving, ~10⁴ events, queries the fold cannot answer, or
deployment beyond one machine. A `postgres-repository.ts` implements two methods
and nothing above it changes.

### 5. Deterministic event model

**Events are the only writable truth.** Canonical state is a fold over them.
v0.2's parallel record tables are deleted.

Every event carries:

```ts
{ id, problemId, actorId, timestamp, objectId, eventType, payload,
  causationId?, correlationId? }
```

Types: `ProblemCreated` · `ContributionAdded` · `ContributionEdited` ·
`RelationProposed` · `RelationAccepted` · `RelationRejected` ·
`ConflictProposed` · `ConflictAccepted` · `ConflictRejected` ·
`EvaluationAdded` · `ContributionSuperseded` · `VisibilityChanged`.

Determinism is bought by **injecting the clock and the id source**. `Date.now()`
and `Math.random()` do not appear in `domain/` or `application/`. Ids are
monotonic and content-independent; tests use a fixed clock and get byte-identical
event streams.

Ordering is the append order of the log. Timestamps are metadata, not the
ordering key — two events in the same millisecond still have a defined order.

`actorId` is copied from the `ActorContext` and from nowhere else. **No curator
code path can construct an event**, which is how "never use AI to manufacture
attribution" becomes a structural property instead of a promise.

### 6. Canonical projection

`project(events) → ProblemState` — a pure fold, no I/O, no clock:

```ts
{ problem, contributions[], relations[], conflicts[], proposals[], events[] }
```

`ContributionSuperseded` sets `status: 'superseded'` and records
`supersededBy`; it never removes the contribution or its events. Rebuilding the
projection from the full log always reproduces current state — asserted by test.

Derived-view discipline is unchanged and now enforced by the data flow: State is
the projection, Map and Timeline are computed from it, and neither can write.

### 7. Conflict model

Conflicts are objects, not error states:

```ts
{ id, problemId, leftObjectId, rightObjectId, conflictType, reason,
  detectedBy, confidence, status, createdAt, reviewedBy?, resolvedBy? }
```

`conflictType` ∈ `source_conflict` · `knowledge_conflict` · `decision_conflict` ·
`assumption_conflict` · `commitment_conflict`.

Lifecycle: a conflict exists **only** as the result of `ConflictAccepted`. AI and
the deterministic curator may only produce *proposals*. A rejected proposal emits
`ConflictRejected` and creates no conflict. `status: 'open'` conflicts are
canonical and unresolved, and the React State view renders them prominently
rather than hiding them.

### 8. Curation proposal model

```ts
{ id, problemId, kind, sourceId, targetId?, relationKind?, conflictKind?,
  suggestedKind?, reason, confidence, proposedBy, status, createdAt,
  reviewedBy?, reviewedAt? }
```

Allowed for v0.3: classify · propose duplicate · propose relation · propose
conflict · short explanation. The deterministic curator runs first and handles
obvious cases; the AI curator receives a **bounded candidate set** (at most 12
contributions from the same problem), never the store.

Not built: autonomous synthesis, automatic consensus, automatic deletion,
automatic supersession, silent merges, automatic visibility changes.

The guarantee is type-level: a curator returns `CurationProposal[]`. Only
`curation-service.review()`, which requires an `ActorContext`, emits
`RelationAccepted` / `ConflictAccepted`.

### 9. Participant identity boundary

**Identity is resolved server-side, from a token, before any service is called.**

```ts
interface TokenVerifier { verify(token: string): Promise<ActorContext> }
interface ActorContext  { actorId: string; displayName: string; scopes: string[] }
```

`TokenVerifier` is deliberately the shape of the SDK's `OAuthTokenVerifier`.

For v0.3 the *issuer* is a dev stub: `POST /api/auth/session { participantId }`
mints an opaque in-memory token for one of Achim · Kai · Lea · Mara. There is no
password and no authorization server. React shows a participant switcher that
calls it; the MCP entrypoints read `BRAINSTORM_TOKEN` from the environment.

This is a **login stub, not a fake security model**, and the distinction is
load-bearing:

- What is fake is *how a principal is established* — one file, `prototype-auth.ts`.
- What is real is *how a principal is carried, verified and used* — bearer token,
  server-side resolution, `ActorContext` threaded explicitly, `401` +
  `WWW-Authenticate` on failure.

Nothing below the adapters ever sees a token, so swapping to OIDC means
implementing `TokenVerifier` against JWKS and serving RFC 9728 metadata. The
thing being removed is a leaf.

By contrast v0.2's `x-brainstorm-actor` had *no* removable seam, because the
caller was the identity provider. The client asserting `"user": "Achim"` is now
structurally impossible: no service reads a name from any request body.

**Recommended future design (explicitly not built):** br-ai-nstorm as an OAuth
2.1 Resource Server against an external OIDC Authorization Server; MCP clients
discover it from the `401` challenge per RFC 9728, with DCR + PKCE;
`AuthInfo.extra` carries the stable subject mapped to `person:*`.

### 10. Review boundary

A mutation is canonical only if a human `ActorContext` authorised it.

| Actor | May do | May never do |
|---|---|---|
| participant | contribute · edit own · review proposals · accept/reject conflicts | — |
| deterministic curator | propose | write any event |
| AI curator | propose (bounded input) | write any event · declare truth · resolve conflict |

Enforced in `domain/policies.ts` and by construction: curator modules do not
import event constructors. `proposedBy` records which curator produced a
proposal (`curator:deterministic`, `curator:openai:<model>`) and is never a
person; `reviewedBy` is always a person.

Contributions are appended **before** curation runs. Curation failure can never
lose a contribution.

### 11. Failure handling

Typed domain errors — `NotFound`, `Invalid`, `Unauthorized`, `Forbidden`,
`Conflict` — raised in the domain, mapped per adapter:

| Domain | HTTP | MCP |
|---|---|---|
| `NotFound` | 404 | `isError: true` result |
| `Invalid` | 422 | `isError: true` result |
| `Unauthorized` | 401 + `WWW-Authenticate: Bearer` | `isError: true` result |
| `Forbidden` | 403 | `isError: true` result |
| `Conflict` | 409 | `isError: true` result |
| unexpected | 500, message not leaked | `isError: true`, message not leaked |

MCP tools do not throw for operation failures — a thrown error is a protocol
fault, while a failed operation is a result the model must be able to read.

The AI curator is best-effort by design: any failure (missing key, network,
malformed output) is logged to **stderr** and skipped. The contribution is
already durable. Deterministic curation is unaffected. Stdout is never written
to by server code, because under `serveStdio` stdout *is* the JSON-RPC channel.

React shows explicit loading / error / empty states and never silently falls
back to local seed data, because silently-local state is the exact illusion this
milestone exists to remove.

### 12. What is deferred

Postgres (trigger recorded in §4) · real OIDC (design recorded in §9) ·
websockets/live push — React refreshes after mutation and on demand · ATProto ·
private cognitive bubbles · aperture permissions · autonomous agents ·
consensus scoring · Kafka · Neo4j · Redis · graph database · dynamic UI ·
project management · social feed.

`EvaluationAdded` and `VisibilityChanged` are defined in the event union and
projected, but no UI drives them yet — they exist so the log shape does not
change when the UI arrives.

## Consequences

**Good.** One registration site serves stdio, HTTP and tests. Four participants
share one process. Attribution cannot be forged by a client or manufactured by
a model. Supersession cannot erase history. Storage is swappable without
touching the ontology. The decisive end-to-end test is expressible.

**Costs, accepted.** More files than v0.2 for the same feature surface —
justified by the boundaries being real rather than conventional. Projecting on
every read is O(events); trivially fine at this size and the recorded trigger for
Postgres is also the trigger for caching folds. JSON remains single-process.
The dev token issuer must be removed before any deployment, and is fenced behind
an explicit flag to make that hard to forget.

**Rejected alternatives.** *Keep the v1 MCP idiom and add features* — cannot
express per-participant identity, and drifts from a moving SDK. *Move to
Postgres now* — changes storage and ontology in the same milestone, so a failing
test cannot say which is wrong. *Keep `x-brainstorm-actor` for one more
milestone* — violates the brief's identity constraint and has no removable seam.
*Adopt Emmett for event sourcing* — no licence grant, stated intent toward
AGPL/SSPL. *Keep records and events in parallel* — two truths that drift.
